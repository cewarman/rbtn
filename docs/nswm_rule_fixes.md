## 評估方法與限制

### 偵測器怎麼運作

錯誤分析用的是規則式偵測器（不在本 repo 內），對每筆標記做：

1. **數值反推**：把唸法中的中文/英文數字反推回數值，與原文的阿拉伯數字比對（已處理百分比、分數、比數、日期、序數、廿/卅、○、萬/億單位等合法唸法）。
2. **邊界檢查**：標記前一字是數字或小數點、後一字是數字、%、小數點+數字、千分位逗號，視為截斷。
3. **結構檢查**：offset 對不回原文、規則欄含非規則內容、原文含 tab、唸法殘留阿拉伯數字、唸法與原文相同。
4. **一致性**：同一原文字串在全語料中的少數派唸法（<10%）。

### 數字的意義

- 偵測器標出的是**疑似錯誤**，不是 ground truth。它有誤報（例如 `二0四0年` 內夾雜 ASCII 0、`40 to 50` 雙空白）也有漏報（唸法錯但數值一致，例如球隊名 `76人` 唸成七十六人）。
- 因此「修正前 vs 修正後」的筆數是**同一把尺量兩次的相對比較**，可以作為工程改善的證據，但不能直接換算成正確率。
- 日/號、星期/禮拜是轉換函式的隨機變體，不算錯誤；比較時已排除。

- 全量重跑時前 79% 用的是修 URL 溢位之前的程式，差異只在小寫百分比編碼網址的唸法（`%e7%a7%91` 現在會解碼成中文），不影響上表的錯誤類別比較。
- 全量數字不含 commit 之後的 R75 英文語境修正（COVID-19 在英文句中被唸兩次，全量僅 149 筆）。

### 過程中額外發現並修正的程式錯誤

- **URLNOR 堆積溢位**（commit 666f15b）：長的百分比編碼網址會讓程式當掉。全量重跑時 8 個分片都因此在約 79% 處中止，用 AddressSanitizer 定位後修正。這個 bug 在修正前的版本就存在，代表原始訓練資料的產生過程也可能在這些檔案上中斷。
- **N2SSTF_LD 英文分支重複輸出**：R75 在英文語境把 COVID-19 唸成「COVID-nineteen COVID- one nine」。

### 若要報告準確率

需要人工標註的黃金子集：從偵測器標記的項目分層抽 300～500 筆，再從未標記的項目抽同量，人工判斷唸法對錯。如此可得偵測器的 precision/recall，以及修正前後在黃金子集上的真實正確率。
